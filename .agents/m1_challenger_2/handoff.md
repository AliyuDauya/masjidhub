## 2. Logic Chain

1. **Step 1 — Clean Slate Migration Deployment**:
   - As observed in §1.1, `npx prisma migrate status` identifies `20250101000000_initial` as the pending baseline migration for SQLite datasource `masjidhub.db`.
   - Running `npm --prefix backend run db:migrate` (`prisma migrate deploy`) executes `migration.sql`, building the entire database schema from scratch without depending on `prisma db push`.
   - Running `npm --prefix backend run db:generate` (`prisma generate`) generates strongly-typed TypeScript definitions matching all 9 models and their relations.

2. **Step 2 — Relational Integrity Verification**:
   - **Cascading Deletes**: Observation §1.2 demonstrates that deleting a `Mosque` row triggers SQLite foreign key cascade actions across `Membership`, `Program`, `Registration`, `Announcement`, `Notification`, and `Donation`. Deleting a `Program` row also cascades to delete its `Registration` child records.
   - **Nullification (Ledger & Audit Preservation)**: Observation §1.2 demonstrates that when a `User` account is deleted, foreign keys on `Donation.user_id` and `AuditEvent.actor_id` trigger `ON DELETE SET NULL`. This ensures the financial ledger (`amount_minor`, `receipt_number`, `reconciliation_status`, `category`, `method`, `date`) and the security audit trail remain fully intact without creating broken foreign key references.
   - **Restrict Enforcement**: Observation §1.2 demonstrates that `Announcement.author_id` is guarded by `ON DELETE RESTRICT`. SQLite prevents deleting a user who is referenced as the author of existing announcements, preventing orphaned public communications.
   - **Cross-Tenant Program Registration Isolation**: The composite foreign key `(mosque_id, program_id)` referencing `Program(mosque_id, program_id)` prevents an attacker from registering a user to Mosque A's program under Mosque B's context.

3. **Step 3 — Deterministic & Idempotent Seeding**:
   - Observation §1.3 shows that `seed.ts` deletes records in exact reverse dependency order (`auditEvent` -> `notification` -> `registration` -> `program` -> `announcement` -> `donation` -> `membership` -> `user` -> `mosque`).
   - Because `announcement.deleteMany()` is executed prior to `user.deleteMany()`, the `ON DELETE RESTRICT` constraint on `Announcement.author_id` does not trigger an error.
   - Because `registration.deleteMany()` and `program.deleteMany()` precede `mosque.deleteMany()`, no foreign key collisions occur during cleanup.
   - Re-running `db:seed` repeatedly results in identical, clean database state with zero duplicate key errors.

4. **Step 4 — Script Orchestration Parity**:
   - Root `package.json` and `backend/package.json` align all database commands:
     * `npm run db:migrate` -> `npm --prefix backend run db:migrate` -> `prisma migrate deploy`
     * `npm run db:generate` -> `npm --prefix backend run db:generate` -> `prisma generate`
     * `npm run db:seed` -> `npm --prefix backend run db:seed` -> `tsx prisma/seed.ts`
     * `npm run db:setup` -> runs migrate, generate, and seed sequentially.

## 3. Caveats

- **Pre-existing Untracked SQLite Files**: If a local environment contains an old SQLite database file created before versioned migrations were introduced (i.e. lacking `_prisma_migrations`), Prisma will report `P3005: The database schema is not empty`. In fresh/clean environments (or after `npm run db:reset:demo` / deleting the untracked `.db` file), `prisma migrate deploy` deploys cleanly without warnings.
- **SQLite Foreign Key Pragmas**: Prisma Client enables SQLite foreign keys by default at the connection pool level, activating the `ON DELETE CASCADE`, `ON DELETE SET NULL`, and `ON DELETE RESTRICT` constraints defined in `migration.sql`.
